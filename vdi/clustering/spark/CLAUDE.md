**Start by reading, in order:** `REVISION_SORTING.md` (design and decisions — why each

## Second workload: Redbench IMDb (R3D4) — `WORKLOAD=imdb`

The same harness also runs a second workload: Redbench's replay of a real Amazon Redshift
trace onto the IMDb (JOB/CEB) queries, answering R3 (D4: "a real workload trace is preferred,
or at least a workload with realistic distribution skews"). Provenance and measurements:
`../../redbench_imdb/README.md`. Steps: NODE_RUNBOOK.md, "Second workload".

- **Select it with `export WORKLOAD=imdb` before `source ./env.sh`**, in every shell. Unset, the
  harness is the TPC-DS setup exactly. With it set, the warehouse, results and plans live under
  `$WORK/imdb/` and the manifest is `manifest_imdb.json`; nothing touches TPC-DS state.
- **Only after the TPC-DS run has finished.** `setup` rebuilds the runner jar (required for
  IMDb) and must not swap it under a running TPC-DS job; the two also share `local[*]`.
- **Stop after the pilot and report per-query runtime** before the configuration runs. Then
  k=2, c=2 only (10 runs, 2,667 query executions) unless Tapan asks for more. Never "all k"
  (63,599 executions).
- Value assignments are the paper's, as for TPC-DS (Tapan, 2026-10-08): Constant, Value 50,
  100, 500, 1000 (`value_iter` 0–4); high = N, medium = N/10, low = 1. High = queries touching
  `cast_info.role_id`; medium = remaining queries touching `name.gender` or
  `name.name_pcode_nf`; low = the rest (345 / 11 / 59 distinct queries; 5.24% / 0.20% /
  94.56% of executions). The tier columns go in the paper: they are recorded in
  `../../redbench_imdb/harness/value_tiers.json` and copied to `$RESULTS/analysis/`.
  Built by `../../redbench_imdb/make_harness_inputs.py`. The earlier role/comp/rare/hot ×
  r : √r : 1 sweep is superseded and was never run. `manifest_imdb.json` was regenerated with
  `plan_layouts.py --keep-ids-from <previous manifest>` so already-built layouts keep their ids.
- Utility is **net utility** (`analyze` defaults to `--weighting executions` for IMDb): each
  query weighted by how often it ran in the trace, normalized to No Sort. Don't switch it.
- `plot` is not adapted for IMDb yet; stop at `analyze` and report.
- **Results (k=2, c=2, 2026-10-08):** `results/imdb/RESULTS_NOTE.md` (TPC-DS: `results/RESULTS_NOTE.md`).

## Layout of this directory

| File | What it does |
|---|---|
| `env.sh` | All paths. Confirm on the node before the first run. |
| `run_phase.sh` | The only entry point: `setup`, `check-source`, `build-base`, `explain`, `build-pilot`, `pilot`, `build-layouts`, `build-configs`, `configs`, `analyze`, `plot`. |
| `manifest.json` (`manifest_imdb.json` for IMDb) | Every configuration (value × strategy × k × c) and the 36 distinct layouts it needs. Generated by `plan_layouts.py` from `../src/rank.py --multi-rowgroup-only`. Source of truth. |
| `queries_spark/` | The 99 DuckDB queries translated to Spark SQL (`translate_queries.py`). Same text as the DuckDB run — required so decisions match across engines. |
| `build_iceberg.py` | Writes the Iceberg baseline and the sorted/partitioned layouts. |
| `make_runs.py` | Writes a runner plan for one phase (`configs`: one run per distinct set of sorted tables, plus No Sort and Frequent's repeat). |
| `runner/` | `SortingRunner` (Scala): runs queries against a layout with the column/table listener attached; records bytes read three ways. Compiles the listener from `../../spark-lineage-api/listener_versions_new/LineageAPI.scala`. |
| `analyze_sweep.py` | Pilot report; configuration utilities from measured bytes only; the paper's `profiles_combined_*.csv`; listener cross-check. |
| `plot_workload_value.py` | The paper's `workload_value.pdf` (bytes) and a rows-read version, from those CSVs. |
